# CLAUDE.md

Classic Arkanoid (Breakout) game. Unity `6000.5.6f1`, Universal Render Pipeline, new Input System.

Gameplay is strictly 2D (2D physics on the XY plane) but the visuals are 3D: bricks, paddle and walls are box meshes, the ball is a sphere, all with URP Lit materials (`Assets/Materials`), lit by the scene's directional light in front of a shadow-catching `Backdrop` plane at z 0.6. The light faces the playfield head-on horizontally and tilts down by `ArkanoidSetup.LightPitch` (30°). Nothing here casts onto a floor — every shadow lands on a surface *behind* its caster — so the shadow's offset from the object is `gap × tan(pitch)`: a steeper, "higher" light smears the shadow further down the backdrop, and a shallower one tucks it back in behind the object. 30° keeps shadows readable as a depth cue without the long drop the earlier 50° gave. The walls use a generated tileable brick-masonry texture (`Assets/Textures/BrickWall.png`, grayscale so the material tint colors it) on custom box meshes (`Assets/Meshes`) authored at final size with world-unit UVs per face — a scaled stock cube would squeeze the texture into stripes on its small faces (end caps, tops). The wall transforms are unit-scale, so their `BoxCollider2D` sizes are set explicitly; the `WallSide`/`WallTop` materials both tile 1:1. The camera is perspective (FOV 50 at z −13.5, framing-equivalent to the old orthographic size 6). Bricks are tinted per instance via `MaterialPropertyBlock` (`Brick.SetColor`), and the crack overlay stays a `SpriteRenderer` child sitting just in front of the box's face.

The paddle has rounded corners: a rounded-rectangle prism mesh (`Assets/Meshes/Paddle.asset`, 2 × 0.4 × 0.5, corner radius 0.15, authored at final size so the transform is unit-scale) paired with a `BoxCollider2D` shrunk by the radius on every side (1.7 × 0.1) plus `edgeRadius: 0.15` — exactly the same rounded rectangle — so the ball's bounce reflects off the corner curve's true normal. `Ball.cs` applies its arcade paddle-bounce override only when the contact normal is straight up (flat-top hits); corner hits keep the engine's reflection.

There are four brick shapes, and each prefab's 2D collider matches its visual outline exactly so the ball reflects off the shape's true contact normal:

- `Brick.prefab` — the normal 1.5 × 0.5 box (scaled stock cube + `BoxCollider2D`).
- `HalfBrick.prefab` — a half-width 0.68 × 0.5 box; two of them plus the level's 0.14 gap fill one normal slot (2 × 0.68 + 0.14 = 1.5).
- `RoundedBrick.prefab` — full-size with corner radius 0.12: a rounded-rectangle prism mesh (`Assets/Meshes/BrickRounded.asset`, built by the same `BuildRoundedPrismMesh` as the paddle, unit-scale transform) with a 1.26 × 0.26 `BoxCollider2D` + `edgeRadius: 0.12`, so corner hits reflect off the curve.
- `RoundBrick.prefab` — a 0.5-diameter sphere (stock sphere at scale 0.5) with a `CircleCollider2D` (radius 0.5 × scale = 0.25 world), so hits deflect along the circle's radial normal. Its crack overlay child is scaled 0.7 (≈ inscribed square) to stay over the circular silhouette.

`GameManager.rowKinds` assigns a shape per row (currently Rounded / Normal / Half / Round / Normal, top to bottom); Half and Round rows spawn two bricks per slot at slot center ± 0.41 and half the row's points each. `PrefabFor` falls back to the normal brick if a variant prefab is unwired. All four prefabs share the white `Brick.mat` tinted per instance, the crack overlay child, and the same `Brick` component — hardness and points are set per spawn.

## The main menu screen

The menu is not a UI panel at all — it is a small playable scene, and there is no UGUI in it. The `MenuScreen` root (authored inactive, carrying `MainMenuPanel` itself) holds an oversized opaque `MenuBackdrop` box at z −3 that covers the camera's frame on any aspect ratio, and in front of it, all on the `MenuPlaneZ` −3.7 plane:

- `MenuTitle` — the word ARKANOID, tilted 8° so its tops and sides catch the light and it throws a shadow onto the backdrop. It is **eight children, one brick per letter**, each with a `MenuTitleBlock` and a `BoxCollider2D` covering the glyph's whole 5 × 7 box (holes included — a collider tracing the strokes would let the ball rattle around inside an O). A hit shatters the letter into `Debris` and switches it off; `MainMenuPanel.Show` switches them all back on, so breaking the word is a toy rather than a permanent edit.
- `MenuPlay` — the part the player drives, grouped so the hall of fame view can drop it and leave the backdrop and title standing. It holds the two option slabs (`MenuOption`, rounded prisms in two of the playfield's brick colours with block-letter labels standing proud of the face), a `MenuPaddle` reusing the playfield paddle's mesh, collider and `Paddle` script, and a `MenuBall` instance of the ball prefab at a gentler speed (6.5 vs the playfield's 8).

**Picking an option means hitting its slab with the ball**, and the slab breaks under it: the hit shatters the slab and its raised label into `Debris` in their own colours (count scaled by width against a brick's, so a 5.8-wide slab isn't rubble-starved) and switches the option off, and `MainMenuPanel` then holds the choice back for `ShatterPause` (0.9 s) before raising `OptionChosen`, so the pieces visibly fall before the screen changes rather than the hit cutting away instantly. `OnOptionHit` returns whether the hit counted, which is what stops the still-live ball from shattering the *other* slab during the pause; `Update` and `BallWaiting` both go quiet once `chosen`. `Show` puts both slabs back the way it puts the title back. Debris fragments are unparented root objects that outlive their spawner, so `Hide` calls `Debris.ClearAll()` — otherwise the menu's rubble would go on raining over the first seconds of the round.

There is no keyboard or mouse path to the options. The ball waits on the paddle until SPACE, exactly like a round — `GameManager.OnGUI` draws the same "press SPACE to launch" prompt (lower on screen for the menu, where mid-screen is where the slabs are). The slabs are sized to their labels rather than to each other, and the gap between them is a real alley, not a margin: the paddle rests under it (`MenuPaddleRestX`, the alley's centre, which unequal slabs put off to one side), so a ball launched straight up picks nothing and the player has to aim.

**The menu's field is unlimited.** `GameManager.playfieldObjects` (the `Walls` root and the playfield `Paddle`) is switched off for the whole `Menu` state and back on in `NewGame`: 2D physics ignores Z, so the playfield's colliders would otherwise fence in the menu's ball even though the menu backdrop hides them, and both paddles would answer the arrow keys at once. A ball that leaves the camera's frame — tested against the actual viewport, so it holds on any aspect ratio — materialises back on the paddle. `Paddle.cs` keeps its own Z rather than zeroing it, so the menu's paddle stays on the menu plane.

The letter meshes come from `BuildBlockMesh`: a 5 × 7 block font (`BlockFont`, the letters of ARKANOID plus the two option labels), one box per horizontal run of solid cells in a glyph row rather than one per cell. UVs are taken from each corner's position plus a `uvOrigin` giving the piece's place in the word (× `MenuTitleUvScale` 2), which is what lets the title be eight independently-built letters whose `BrickWall.png` masonry still runs continuously across the joins, at one 0.5 × 0.25 texture brick per 0.25-unit glyph cell. The offset only ever moves the axis it belongs to, so the side faces (mapped from Z) stay put whatever a piece's X. The 47-cell word spans 11.75 units, which stays inside the frame down to 4:3.

## Layout

- `Assets/Scripts/Paddle.cs` — keyboard paddle movement (`Keyboard.current`, arrows/A-D), clamped to the playfield.
- `Assets/Scripts/Ball.cs` — constant-speed ball with a `Damage` value (currently 1) read by bricks on impact. Kinematic and paddle-following while attached; dynamic after launch. `FixedUpdate` renormalizes velocity to `speed` and enforces a minimum vertical component so the ball can't get stuck bouncing horizontally. Paddle bounces off the flat top override the physics reflection with an angle based on where the ball hit the paddle; hits on the paddle's rounded corners (tilted contact normal) keep the engine's reflection off the curve.
- `Assets/Scripts/Brick.cs` — accumulates the ball's `Damage` per hit against its `Hardness` (1–3, set per row by `GameManager`); destroys itself and reports its `Points` to `GameManager` once damage reaches hardness, spawning falling `Debris` fragments in its color as it goes. While still alive it shows a crack overlay on the prefab's `Cracks` child renderer — light crack up to half damage, heavy crack beyond — from parallel arrays of sprite variants wired in by the editor setup script. On its first hit each brick picks a random variant index plus random X/Y renderer flips, then keeps them, so cracks differ between bricks while escalating damage reads as the same crack spreading (each heavy sprite extends its light counterpart).
- `Assets/Scripts/Debris.cs` — cosmetic rubble for a shattering brick, spawned by `Brick` at destruction (runtime-only, nothing to author in the editor). 6–9 small cube fragments share the brick's material, tinted with per-fragment brightness variation of the brick's color via `MaterialPropertyBlock`; the cube mesh is lifted once off a throwaway `CreatePrimitive` template. Fragments carry no physics components — they are moved by hand in `Update` (initial outward/upward pop, constant gravity, random tumble), so they can never disturb the 2D gameplay colliders; they shrink away over the last third of a 1.2–2 s life (the opaque Lit material can't alpha-fade) and also die below the playfield. `Spawn` takes an optional `amount` multiplier on the fragment count for casters bigger than a brick (the menu's option slabs), and `ClearAll` sweeps every fragment still in the air, for screen changes that would otherwise inherit the last screen's rubble.
- `Assets/Scripts/GameManager.cs` — state machine (Menu/Ready/Playing/EnteringName/GameOver/Won), score, lives, high score persisted via `PlayerPrefs` (`Arkanoid.HighScore`), runtime brick-grid construction (per-row color and hardness: red rows take 3 hits, blue rows 1). The high score is still tracked and persisted, but it is no longer displayed anywhere — it only decides whether a finished round earns a `RecordBook` entry, and the hall of fame is where the numbers are read. The HUD is hidden on the menu and shows score and lives during a round. When a round ends above the record held at round start, switches to `EnteringName`: captures the player's name via `Keyboard.onTextInput` (backspace edits, ENTER submits, 12-char cap) and appends a `RecordBook` entry. Pushes values into the `ScoreBoard` and drives the `RecordsPanel` and `MainMenuPanel`, and switches `playfieldObjects` (the walls and the paddle) off for the menu and back on for a round. OnGUI is used for the "press SPACE to launch" banner, which serves the menu's ball as well as a round's, and for the quit confirmation. **ESC leaves a round for the menu, on confirmation**: the prompt sets `Time.timeScale` to 0 so a ball in flight can't be lost while the player reads the question, and swallows every key but its own (Y/ENTER leaves, N/ESC keeps playing). It is only offered from `Ready` and `Playing` — the menu has nothing to leave, name entry is one ENTER from being submitted, and an end screen just goes back on ESC as it does on SPACE. Abandoning a round winds the stored high score back to `previousRecord`, because `SetScore` has been pushing the running score into it all round and a walked-out-on score must not raise the bar the next round has to beat. `ShowMenu` now calls `ClearRound` (ball, brick grid, any name-entry subscription): 2D physics ignores Z, so a ball or a grid of bricks left standing behind the menu's backdrop would still be in the menu ball's way, unseen — which is the same reason `playfieldObjects` goes off. Freezing time is not enough on its own for the components that read the keyboard themselves, so `MainMenuPanel.Update` bails out on `GameManager.Paused` rather than launching the menu's ball behind the prompt; the paddle needs no such guard because it moves by `Time.deltaTime`. Boots into the `Menu` state and reacts to `MainMenuPanel.OptionChosen` (start a game / show the hall of fame, which ESC, SPACE or ENTER leaves); end screens go back to the menu on SPACE. Every state transition stamps `transitionFrame` and `Update` returns early on that frame, because `MainMenuPanel` reads the same keyboard in the same frame in an undefined order — without it the ENTER that picks `START` would also launch the ball. Serialized references are wired by the editor setup script.
- `Assets/Scripts/ScoreBoard.cs` — display-only UGUI HUD component on the `ScoreBoard` canvas (Score / Lives). The readouts sit under a `Hud` child, so `SetVisible` can switch the whole HUD off for the menu screen without touching the records and main menu panels on the same canvas; `GameManager` pushes the values in and shows the HUD for a round. There is no high score readout.
- `Assets/Scripts/RecordBook.cs` — static store for the chronological record-holder list (date/name/score), persisted in `PlayerPrefs` (`Arkanoid.Records`) as JSON.
- `Assets/Scripts/RecordsPanel.cs` — display-only end-of-round overlay under the `ScoreBoard` canvas: name entry after a new record, then the hall-of-fame list. Authored inactive; `GameManager` shows/hides it (also reused from the menu's "hall of fame" option).
- `Assets/Scripts/MainMenuPanel.cs` — the title screen, which is scene content rather than UI (see "The main menu screen" above). The component sits on the `MenuScreen` root, so `Show`/`Hide` is just switching that subtree on and off; `HideOptions` drops only the `MenuPlay` group, so the menu's hall of fame view keeps the backdrop and title behind the records panel and a stray bounce can't pick an option. It reassembles the title and the option slabs, parks the paddle back in the alley and re-attaches the ball on `Show`, launches on SPACE, and materialises the ball back on the paddle whenever it leaves the camera's frame. `MenuOption` (on each slab) reports a ball hit to it, and it raises `OptionChosen` for `GameManager` — first hit wins, since the ball is still live for the frames it takes to switch away.
- `Assets/Scripts/MenuOption.cs` — one option slab; a ball collision is the entire interaction. A counted hit shatters the slab and its label into `Debris` and switches the option off, the same toy the title letters are.
- `Assets/Scripts/MenuTitleBlock.cs` — one letter of the title; a ball collision shatters it into `Debris` and switches it off.
- `Assets/Editor/ArkanoidSetup.cs` — `[InitializeOnLoadMethod]` script that generates the sprite textures (`Assets/Sprites`), configures their importers, creates the bouncy `PhysicsMaterial2D` (`Assets/Physics`) and the `Ball`/`Brick` prefabs (`Assets/Prefabs`), then authors the camera, walls, paddle, and wired `GameManager` into the scene, and finally the `ScoreBoard` screen-space canvas. Editor-authored content stays inspectable without Play mode; only the ball and bricks exist at runtime.

## Editor setup is staged and resumable

`ArkanoidSetup.Setup()` performs **one** stage per domain reload and returns, relying on the next reload to observe the previous stage's output (textures → importers → physics material → prefabs → scene → scoreboard UI → records panel → deferred save → crack texture variants → crack importers → brick-prefab crack overlay → Lit materials → ball prefab to sphere → brick prefab to box → 3D scene retrofit → deferred save → squared wall corners → deferred save → brick wall texture → textured wall materials → wall material swap → deferred save → world-UV wall meshes → wall mesh swap → deferred save → randomized-crack prefab retrofit → rounded paddle mesh → paddle mesh/collider swap → deferred save → centered light position → deferred save → centered light direction → deferred save → rounded brick mesh → brick variant prefabs → GameManager variant wiring → deferred save → menu block meshes → menu materials → menu screen → deferred save → grouped HUD without its high score → deferred save → flattened light tilt → deferred save → menu panel stripped to its options → deferred save → menu rebuilt as a playable screen → deferred save). Stages 9 and 10 authored the menu as a UGUI panel and are gone now that the menu is scene content; the numbering after them was left alone rather than shuffled. The crack textures are generated from a per-variant seeded `System.Random` walk (`Assets/Sprites/CrackLight0-3.png` / `CrackHeavy0-3.png`), so a from-scratch rebuild reproduces the same set. Every stage that edits the scene only marks it dirty; a paired follow-up stage saves it from a self-removing `EditorApplication.update` handler on the next editor tick, to avoid the modal dialog described below. This works around `AssetDatabase` writes not being reliably readable back via `LoadAssetAtPath` within the same call. If you touch this file, preserve the one-stage-per-reload structure. The scene stage is guarded by `GameObject.Find("GameManager")`, so once set up the whole method is a no-op.

Folder existence is checked on disk (`System.IO.Directory`) rather than via `AssetDatabase.IsValidFolder`, which can go stale in driven sessions.

**Caution:** the scene stage calls `EditorSceneManager.SaveScene` from `[InitializeOnLoadMethod]`; in one session Unity then detected the open scene's file change and raised a *modal* "scene changed on disk" dialog that blocked the Editor main thread (and the Uplink bridge) until dismissed by hand. Either button is safe (disk and memory content are identical), but be aware programmatic scene saves can trigger it.

Use the `unity-game-design` skill for the general pattern this file follows when making further Editor-script changes here.
